<critical_rules priority="absolute">
  <rule id="core_contexts_first">Сначала сосредоточиться на тактическом моделировании Основных поддоменов. Применять к Поддерживающим только если время и сложность оправдывают это.</rule>
  <rule id="invariants_required">Каждый агрегат должен иметь хотя бы один задокументированный инвариант. Агрегат без инвариантов — просто контейнер данных, его существование следует поставить под сомнение.</rule>
  <rule id="events_from_facts">Доменные события должны представлять то, что уже произошло (прошедшее время). Никогда не моделировать будущие намерения как события.</rule>

</critical_rules>

## Шаг 1 — Моделирование агрегатов

### Что такое агрегат?

Агрегат — это кластер доменных объектов, рассматриваемых как единое целое для изменений данных. Он имеет:
- **Корень агрегата** — единственная точка входа для внешнего доступа
- **Инварианты** — бизнес-правила, которые всегда должны быть истинными
- **Границу транзакции** — изменения внутри агрегата атомарны

### Вопросы интервью

Для каждого ограниченного контекста:

```
Контекст: [Название контекста]

1. Каковы основные «вещи» в этом контексте, имеющие идентичность и жизненный цикл?
   (Это ваши кандидаты на агрегаты)

2. Для каждого кандидата:
   а. Какие бизнес-правила должны быть ВСЕГДА истинными?
      (например, «Итог заказа всегда должен равняться сумме позиций»)
   б. Какие операции можно выполнять над ним?
      (например, разместить, подтвердить, отменить, отправить)
   в. Какие другие объекты всегда сопровождают его и не имеют смысла отдельно?
      (например, ПозицияЗаказа не имеет смысла без Заказа)

3. Можно ли ссылаться на какие-либо из этих кандидатов по ID из других агрегатов,
   а не встраивать их?
   (Держите агрегаты небольшими — ссылайтесь по ID через границы)
```

### Результат — Определения агрегатов

```markdown
## Агрегаты — [Название контекста]

### Агрегат: Заказ

**Корень**: Заказ
**Идентичность**: ИдЗаказа (UUID)

**Инварианты**:
- Итог должен равняться сумме цен × количеств всех ПозицийЗаказа
- Нельзя отменить после отправки
- Должен содержать хотя бы одну ПозициюЗаказа

**Операции**:
- `разместитьЗаказ(идКлиента, позиции[])` → событие ЗаказРазмещён
- `подтвердитьЗаказ()` → событие ЗаказПодтверждён
- `отменитьЗаказ(причина)` → событие ЗаказОтменён
- `отправитьЗаказ(номерОтслеживания)` → событие ЗаказОтправлен

**Сущности внутри агрегата**:
- ПозицияЗаказа (нет идентичности вне Заказа)

**Ссылки по ID** (не встроены):
- ИдКлиента → агрегат Клиент (контекст Идентификации)
- ИдПродукта → агрегат Продукт (контекст Каталога)

---

### Агрегат: [Следующий агрегат]
...
```

## Шаг 2 — Определение объектов-значений

### Что такое объект-значение?

Объект-значение не имеет идентичности — он определяется исключительно своими атрибутами. Два объекта-значения с одинаковыми атрибутами равны. Объекты-значения неизменяемы.

### Вопросы интервью

```
Для контекста: [Название контекста]

1. Есть ли концепции, определяемые исключительно своими атрибутами,
   без необходимости в уникальном ID?
   (например, Деньги, Адрес, ДиапазонДат, АдресEmail, НомерТелефона)

2. Есть ли атрибуты, которые всегда используются вместе и имеют правила валидации?
   (например, Валюта + Сумма всегда идут вместе → объект-значение Деньги)

3. Есть ли доменно-специфические форматы или ограничения на простые типы?
   (например, НомерЗаказа должен соответствовать паттерну ЗАК-ГГГГ-НННННН)
```

### Результат — Объекты-значения

```markdown
## Объекты-значения — [Название контекста]

| Объект-значение | Атрибуты | Правила валидации | Используется в |
|-----------------|----------|-------------------|----------------|
| Деньги | сумма: Decimal, валюта: ISO4217 | сумма ≥ 0, валюта должна быть допустимой | Заказ, Счёт |
| Адрес | улица, город, индекс, страна | Все поля обязательны, формат индекса по стране | Заказ (доставка) |
| НомерЗаказа | значение: String | Должен соответствовать ЗАК-ГГГГ-НННННН | Заказ |
```

## Шаг 3 — Доменные события

### Что такое доменное событие?

Доменное событие фиксирует нечто значимое, произошедшее в домене. Оно:
- Называется в **прошедшем времени** (ЗаказРазмещён, а не РазместитьЗаказ)
- **Неизменяемо** — это произошло, изменить нельзя
- Факт, на который могут реагировать другие части системы

### Вопросы интервью

```
Для контекста: [Название контекста]

1. Какие значимые события происходят в этом контексте, которые могут
   интересовать другие части системы?

2. Для каждого события:
   а. Что его инициировало? (какая операция агрегата)
   б. Какие данные оно несёт? (достаточно для потребителей без обратного запроса)
   в. Кто его потребляет? (другие контексты, проекции, уведомления)

3. Есть ли события, которые должны инициировать длительные процессы
   через несколько агрегатов или контекстов? (Возможно, нужны саги)
```

### Результат — Доменные события

```markdown
## Доменные события — [Название контекста]

### Событие: ЗаказРазмещён

**Инициатор**: операция Заказ.разместитьЗаказ()
**Полезная нагрузка**:
```json
{
  "идСобытия": "uuid",
  "произошлоВ": "ISO8601",
  "идЗаказа": "uuid",
  "идКлиента": "uuid",
  "позиции": [{ "идПродукта": "uuid", "количество": 2, "ценаЗаЕдиницу": { "сумма": 29.99, "валюта": "RUB" } }],
  "итоговаяСумма": { "сумма": 59.98, "валюта": "RUB" }
}
```
**Потребители**:
- Контекст Биллинга → создать Счёт
- Контекст Уведомлений → отправить email подтверждения
- Аналитика → зафиксировать событие продажи

---

### Событие: ЗаказОтменён
**Инициатор**: Заказ.отменитьЗаказ()
**Полезная нагрузка**: `{ идСобытия, произошлоВ, идЗаказа, причина, отменилКто }`
**Потребители**: Биллинг (аннулировать счёт), Склад (освободить товар), Уведомления (отправить отмену)
```

## Шаг 4 — Контракты репозиториев

### Вопросы интервью

```
Для каждого агрегата:

1. Как будет извлекаться этот агрегат?
   (Только по ID? По статусу? По диапазону дат? По клиенту?)

2. Есть ли сложные потребности в запросах, выходящие за рамки простого поиска?
   (Возможно, нужны отдельные модели чтения — см. событийные паттерны ниже)

3. Каковы границы транзакций?
   (Какие операции должны быть атомарными? Какие могут быть eventually consistent?)
```

### Результат — Контракты репозиториев

```markdown
## Контракты репозиториев — [Название контекста]

### РепозиторийЗаказов

```typescript
interface РепозиторийЗаказов {
  найтиПоId(id: ИдЗаказа): Promise<Заказ | null>;
  найтиПоИдКлиента(идКлиента: ИдКлиента): Promise<Заказ[]>;
  найтиПоСтатусу(статус: СтатусЗаказа): Promise<Заказ[]>;
  сохранить(заказ: Заказ): Promise<void>;
  // Примечание: нет удаления — заказы никогда не удаляются, только отменяются
}
```

**Граница транзакции**: Каждый сохранить() атомарен внутри агрегата Заказ.
**Согласованность**: Строгая внутри контекста. Eventual consistency между контекстами через события.
```

## Шаг 5 — Оценка событийных паттернов

Ответьте на эти вопросы, чтобы определить, нужны ли CQRS или событийный источник:

```
1. Нужно ли отвечать на вопрос «каким было состояние X в момент времени T в прошлом»?
   → Если да: рассмотрите Event Sourcing

2. Ваши запросы на чтение имеют очень разную форму по сравнению с операциями записи?
   (например, сложные отчётные запросы vs. простые командные операции)
   → Если да: рассмотрите CQRS с отдельными моделями чтения

3. Нужен ли полный журнал аудита каждого изменения?
   → Если да: рассмотрите Event Sourcing

4. Есть ли длительные процессы, охватывающие несколько агрегатов или контекстов?
   → Если да: рассмотрите Саги / Менеджеры процессов
```

### Результат — Решение по событийным паттернам

```markdown
## Оценка событийных паттернов — [Название контекста]

| Паттерн | Нужен? | Обоснование |
|---------|--------|-------------|
| CQRS | Да / Нет | [причина] |
| Event Sourcing | Да / Нет | [причина] |
| Саги | Да / Нет | [причина] |
| Проекции | Да / Нет | [причина] |

### Модели чтения (если CQRS = Да)

| Проекция | Цель | Исходные события | Обновляется |
|----------|------|------------------|-------------|
| ПросмотрСводкиЗаказов | Список заказов на дашборде | ЗаказРазмещён, ЗаказОтправлен, ЗаказОтменён | Обработчик событий |
| ИсторияЗаказовКлиента | Портал клиента | Все события Заказа | Обработчик событий |
```

## Примечания по адаптации

- **Режим корректировки**: Спрашивайте: *«Есть ли у вас существующие определения агрегатов или схемы событий? Вставьте их, и я определю, что отсутствует или устарело.»*
- **Простые домены**: Если агрегаты не имеют значимых инвариантов — рекомендуйте более простой CRUD-подход и зафиксируйте это в ADR.
- **Event Sourcing**: Рекомендуйте только если пользователь ответил «да» хотя бы на 2 из 4 вопросов об событийных паттернах.
- **Саги**: Если выявлены — отметьте как отдельный результат. Проектирование саг сложно и должно быть отдельной сессией.
