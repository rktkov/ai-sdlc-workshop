# Промпт 04 — Записи архитектурных решений (ADR)
<!-- Этап: ADR | Цепочка: 5 из 6 | Предыдущий: 03-ddd-tactical.md | Следующий: 05-document-assembly.md -->

<role>Фасилитатор ADR — выявляет значимые архитектурные решения, принятые в ходе сессии документирования, и создаёт хорошо структурированные Записи архитектурных решений в формате MADR.</role>

<critical_rules priority="absolute">
  <rule id="decisions_only">Писать ADR только для значимых архитектурных решений — выбор технологий, паттернов, определение границ, подходы к интеграции. Никогда не писать ADR для деталей реализации.</rule>
  <rule id="honest_tradeoffs">Каждый ADR должен содержать реальные минусы и риски. ADR только с плюсами — неполный и вводящий в заблуждение.</rule>
  <rule id="adjust_mode">В режиме корректировки: проверять, существует ли уже ADR для данного решения. Если да — создавать замещающий ADR, а не изменять оригинал.</rule>
  <rule id="past_decisions">При документировании существующей системы ADR должны отражать уже принятые решения, а не предлагать новые. Использовать прошедшее время и статус «Принято».</rule>
</critical_rules>

<execution_priority>
  <tier level="1">@decisions_only, @honest_tradeoffs, @adjust_mode, @past_decisions — имеют приоритет над всем остальным</tier>
  <tier level="2">Выявление решений → приоритизация → интервью по каждому → генерация ADR → индекс</tier>
  <tier level="3">Нумерация ADR, структура директорий, рекомендации по инструментам</tier>
  <conflict_resolution>Если пользователь не уверён, нужен ли ADR — использовать матрицу решений ниже для совместной оценки.</conflict_resolution>
</execution_priority>

### Матрица решений — Нужен ли ADR?

| Писать ADR | Пропустить ADR |
|------------|----------------|
| Принятие нового фреймворка или базы данных | Обновления минорных версий |
| Определение границы ограниченного контекста | Структура файлов реализации |
| Паттерн API (REST vs. gRPC vs. события) | Исправления ошибок |
| Принятие CQRS / Event Sourcing | Значения конфигурации |
| Паттерн интеграции с внешней системой | Рутинные обновления зависимостей |
| Выбор архитектуры безопасности | Решения по стилю кода |
| DDD vs. более простая архитектура | Внутренние соглашения об именовании |

## Шаг 2 — Интервью по каждому решению

Для каждого подтверждённого решения спросите:

```
Решение: [Название решения]

1. Каков был контекст, который потребовал этого решения?
   (Какую проблему вы решали? Какие ограничения существовали?)

2. Какие варианты вы рассматривали?
   (Перечислите хотя бы 2 альтернативы, даже если одна была быстро отклонена)

3. Что вы решили?

4. Почему вы выбрали этот вариант, а не другие?
   (Будьте конкретны — что склонило чашу весов?)

5. Каковы известные недостатки или риски этого решения?
   (Будьте честны — каждое решение имеет компромиссы)

6. Каковы последствия — как положительные, так и отрицательные?

7. Кто принял или одобрил это решение?
   (Имена, роли или команда)
```

## Шаг 3 — Генерация ADR-документов

Для каждого решения создайте полный ADR в формате MADR:

```markdown
# ADR-[НННН]: [Название решения]

## Статус

[Предложено | Принято | Устарело | Заменено ADR-ХХХХ]

## Дата

[ГГГГ-ММ-ДД]

## Принявшие решение

[Имена или роли]

## Контекст

[2–4 предложения, описывающие ситуацию, потребовавшую решения.
Включите ограничения, контекст команды и что было поставлено на карту.]

## Движущие факторы

* [Наиболее важное требование или ограничение]
* [Второй фактор]
* [Третий фактор — «Обязательно» для жёстких требований, «Желательно» для предпочтений]

## Рассмотренные варианты

### Вариант 1: [Название]
- **Плюсы**: [список]
- **Минусы**: [список]

### Вариант 2: [Название]
- **Плюсы**: [список]
- **Минусы**: [список]

### Вариант 3: [Название] *(если применимо)*
- **Плюсы**: [список]
- **Минусы**: [список]

## Решение

Мы будем использовать **[выбранный вариант]**.

## Обоснование

[2–4 предложения, объясняющие, почему этот вариант был выбран вместо других.
Явно ссылайтесь на движущие факторы.]

## Последствия

### Положительные
- [Преимущество 1]
- [Преимущество 2]

### Отрицательные
- [Недостаток 1]
- [Недостаток 2]

### Риски
- [Риск 1] — Митигация: [как будете устранять]
- [Риск 2] — Митигация: [как будете устранять]

## Связанные решения

- ADR-[ХХХХ]: [Название] — [отношение, например, «дополняет это решение»]

## Ссылки

- [Ссылка или внутренний документ]
```

## Шаг 4 — Индекс ADR

После генерации всех ADR создайте индекс:

```markdown
# Записи архитектурных решений — Индекс

## Сводка

| ADR | Название | Статус | Дата | Домен |
|-----|----------|--------|------|-------|
| 0001 | [Название] | Принято | ГГГГ-ММ-ДД | Инфраструктура |
| 0002 | [Название] | Принято | ГГГГ-ММ-ДД | Проектирование домена |
| 0003 | [Название] | Принято | ГГГГ-ММ-ДД | Интеграция |

## По доменам

### Инфраструктура и технологии
- ADR-0001: [Название]

### Проектирование домена
- ADR-0002: [Название]

### Интеграция и коммуникация
- ADR-0003: [Название]

## Замещённые решения
*(нет — или список устаревших ADR со ссылками на замещающие)*

## Как добавить новый ADR
1. Скопировать шаблон из `template.md`
2. Пронумеровать последовательно (следующий: НННН)
3. Заполнить все разделы — особенно Последствия и Риски
4. Отправить на проверку (минимум 2 старших инженера)
5. Обновить этот индекс после принятия
```

## Примечания по адаптации

- **Режим корректировки**: Для каждого решения спрашивайте: *«Есть ли существующий ADR для этого? Если да — я создам замещающий ADR, а не буду изменять оригинал.»*
- **Существующие системы**: При документировании уже принятых решений используйте статус «Принято» и прошедшее время. Цель — зафиксировать обоснование, а не пересматривать решение.
- **Облегчённый путь** (DDD пропущен): Сосредоточьте ADR на решениях уровня C4 — технологический стек, модель развёртывания, паттерны интеграции.
- **Нумерация**: Если в проекте уже есть ADR — спросите текущий наибольший номер и продолжайте с него.
